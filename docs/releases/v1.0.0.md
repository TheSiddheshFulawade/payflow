# PayFlow v1.0.0

Three Spring Boot services (payment, wallet, risk) take each payment through an orchestrated saga over Kafka: hold
the money, check risk, capture. Every payment ends `COMPLETED`, `REVERSED` (any hold returned before capture; there are
no refunds) or `REJECTED`. Open source (MIT). **Nothing is hosted**: you run it on your own machine with Docker Compose.
No real money moves: a capture is a transfer between two demo wallet rows in one database.

## What is checked

After every system and chaos run, `InvariantChecker` checks six invariants over the run's payments and wallets:
money is conserved (`available + held` equals what was seeded), nothing stays held, every payment ends in a final
state, a completed payment has exactly one debit of the payer's held balance and one credit of the payee's available
balance, a reversed or rejected payment moved no money, and one (client, `Idempotency-Key`) creates one payment. Each
chaos test also asserts the exact count of payments per final state. jqwik properties drive the real saga state
machine against a lossy, duplicating, reordering network. Passing tests show that no violation was found in those
runs; they are not a formal proof.

## Results, with their conditions

| Scenario | Fault | Payments | COMPLETED / REVERSED / REJECTED | Laptop time | GitHub time |
| -------- | ----- | -------- | ------------------------------- | ----------: | ----------: |
| C1 | wallet-service killed, restarted after 5 s | 40 | 15 / 5 / 20 | 49 s | 49 s |
| C2 | Kafka broker restarted | 40 | 15 / 5 / 20 | 11 s | 10 s |
| C3 | risk-1 killed; risk-2 alone, plus 7 payments from one payer | 47 | 20 / 7 / 20 | 50 s | 50 s |
| C4 | payment-service paused for 45 s, past every step deadline | 40 | 15 / 5 / 20 | 51 s | 50 s |
| C5 | every request sent 3 times at once with one key, plus C1's kill | 40 from 120 requests | 15 / 5 / 20 | 116 s | 49 s |

Time is the whole scenario, from seeding its wallets to the invariant check, and includes the injected outage or
pause; the C5 laptop slowdown was not investigated. All six invariants held in every run. One run of each scenario on each machine; not a benchmark. Laptop: AMD Ryzen 7
5800H, 15.4 GB RAM, Windows 11, Docker Desktop 28.1.1, 2026-11-28. GitHub: `system` job, `ubuntu-24.04`, JDK 25,
[run 46152086282](https://github.com/TheSiddheshFulawade/payflow/actions/runs/46152086282).

Reconciliation (Spring Batch): 10,000 payments in 2.4 s and 100,000 in 19.3 s of job time, every pair `MATCHED`. The
rows were seeded on a closed business date (the job only reconciles dates up to today minus 2), not sent through the
saga, as a consistent 80/10/10 mix with no breaks, so this measures throughput, not break detection; one run each on the laptop above. Details:
[docs/results/PF-10-measured-run.md](../results/PF-10-measured-run.md).

## How to run

Needs Git, JDK 21 or newer, and Docker with at least 6 GB for its VM.

```bash
git clone --branch v1.0.0 https://github.com/TheSiddheshFulawade/payflow.git
cd payflow
./mvnw -DskipTests package
docker compose -f deploy/compose.yaml up -d --build --wait
./deploy/demo.sh          # Windows PowerShell: ./deploy/demo.ps1
```

Expected: 2 `COMPLETED`, 1 `REVERSED` (over the single-payment risk limit, checked after the hold) and 1 `REJECTED`
(more than the payer has).

## Known issues and what is not proven

- C6 (two payment-service instances at once) was cut (SPEC section 8); the optimistic `version` guard is checked by
  integration tests in which two handlers race, not by two running instances.
- Every result comes from one laptop or one GitHub runner, one run each. The chaos runs do not run reconciliation.
- `demo.ps1` was run against the stack; `demo.sh` was only syntax-checked (`bash -n`). The demo run used
  `compose build` then `up -d --wait`, before a later fix to how the risk image is built.
- `SafeIds.sqlList` in the system tests turns an empty list into `in ()`, invalid SQL; no current caller passes an
  empty list. It is an open learning exercise (a disabled `TODO-ME` test in `SafeIdsTest`), like the other `TODO-ME`
  items.
- Velocity is approximate under failure: during a Hazelcast split or after both members restart a payer may pass more
  than 5 payments in a window. Money rules and the daily total are in PostgreSQL and stay exact.
- Container images are pinned by exact tag, not by digest. The passwords and secrets in `deploy/` are local demo
  values.
- Security limits of the demo stack (from the pre-release security review, nothing exploitable from outside the
  machine): Kafka and Hazelcast are inside the trust boundary, unauthenticated and plaintext on 127.0.0.1, so a local
  process could publish wallet commands without a JWT; real use needs SASL or mTLS and topic ACLs. Keycloak runs in
  `start-dev` with a public client and the password grant, over plain HTTP. The CI Maven mirror fallback is trusted
  without a separate checksum or signature policy.
- The Maven project version and the locally built app image tags are still `0.1.0-SNAPSHOT`; the release is the git
  tag `v1.0.0`.
- Not hosted, not a production system.
